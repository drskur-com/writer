# ADR-0024: 메모의 할 일은 원문을 유일한 저장소로 두고, 할 일 화면은 메모를 훑어 모은 색인으로 만든다

- 상태: Proposed
- 날짜: 2026-10-22
- 관련: ADR-0023(에디터 체크 상자), ADR-0005(그룹 메타) · `src/markdown/tasks.rs`(`todos`), `src/library/todos.rs`(`TodoIndex`), `src/cache.rs`(`Cache`), `src/library/files.rs`(`GroupKind`)

## 배경 (Context)

메모에 적은 할 일(`- [ ] …`)을 따로 모아 보고, Things 3 수준의 정보(메모·체크리스트·예정일·마감일·태그·
완료 기록)를 넣고 싶다.

- 시트는 일반 `.md`다. 할 일 정보도 원문에 남아야 다른 도구에서 읽힌다.
- Markdown 표준에는 마감일 문법이 없다. 할 일 항목(GFM)과 항목 아래 들여 쓴 문단·하위 목록(CommonMark)만 표준이다.

## 결정 (Decision)

**할 일의 원본은 메모 원문이다. 할 일 화면은 메모를 훑어 만든 색인이고, 거기서 고치면 원문의 그 줄에 다시 쓴다.**

- 범위: 메모(`Notes/`) 섹션의 시트만 훑는다. 프로젝트 원고의 체크 목록은 책 내용일 수 있어 섞지 않는다.
- 표기: Obsidian Tasks 관례를 따른다. 다른 도구에서는 글자로 보일 뿐 원문이 깨지지 않는다.

| 정보 | 원문 |
| --- | --- |
| 제목 | `- [ ] 출판사 미팅` (GFM) |
| 메모 | 항목 아래 들여 쓴 문단 (CommonMark) |
| 체크리스트 | 항목 아래 들여 쓴 `- [ ]` 하위 항목 |
| 예정일(언제) | `⏳ 2026-10-25` |
| 마감일 | `📅 2026-10-30` |
| 태그 | `#출판` |
| 완료일 | 체크할 때 `✅ 2026-10-22`를 붙인다 |

```markdown
- [ ] 출판사 미팅 ⏳ 2026-10-25 📅 2026-10-30 #출판
  원고 3장, 표지 시안 챙기기
  - [ ] 원고 출력
  - [x] 표지 시안 받기
```

- 색인(캐시): 라이브러리를 열 때 백그라운드에서 메모를 한 번 훑어 메모리에 `경로 → (수정 시각, 크기, 할 일들)`을
  만든다. 이후에는 폴더 감시가 알려 준 파일만 다시 읽는다. 메모리 색인은 늘 있다(원문 위치를 아는 곳이 색인이다).
  - 디스크 캐시: redb(순수 Rust 키-값, 파일 하나, ACID). 위치는 동기화되지 않는 OS 캐시 폴더
    `<cache_dir>/Writer/<라이브러리 경로 FNV-1a 해시>/cache.redb`다. 키는 메모의 라이브러리 기준 상대 경로, 값은
    그 파일의 `(수정 시각, 크기, 할 일들)` JSON이다. 바뀐 파일 몫만 한 트랜잭션으로 쓴다. 읽기 규칙 버전
    (`PARSER_VERSION`)이 다르면 버리고 다시 읽는다. 다른 창이 캐시를 열었거나 깨졌으면 캐시 없이(또는 새로 만들어) 쓴다.
  - 다른 파생 데이터도 같은 파일에 자기 테이블로 둘 수 있다(`crate::cache::Cache`).
  - 측정(메모 3,000개·할 일 6,000개, release): 캐시 없이 처음 약 470ms(파일 읽기), 캐시가 있으면 약 57ms(그중
    폴더 훑기·stat 50ms, 캐시 읽기 7ms). 캐시 파일 약 4MB.
  - 할 일 하나의 색인 항목: 원문 위치(메모 경로, 할 일 줄 번호, 항목 블록 = 할 일 줄부터 그 아래 들여 쓴
    메모·체크리스트 끝까지의 줄 범위), 블록 원문 사본, 읽어 낸 값(제목·체크·예정일·마감일·완료일·태그·메모·
    체크리스트).
  - 스캔은 파일 전체를 보므로 코드 블록·frontmatter 안의 줄은 할 일로 보지 않는다(에디터의 줄 판정보다 정확하다).
- 원문에 다시 쓰기: 할 일 화면에서 고친 내용은 항상 원문 메모에 반영한다.
  1. 색인 항목의 원문 위치로 간다. 쓰기 직전에 파일을 다시 읽어 블록이 사본과 같은지 확인한다. 밀렸으면 같은 블록을
     찾고, 없거나 여럿이면 쓰지 않고 다시 스캔한 뒤 알린다.
  2. 바뀐 부분만 원문 표기로 쓴다(체크 → `[ ]`↔`[x]`와 `✅ 날짜`, 마감일 → `📅 …`, 메모·체크리스트 → 들여 쓴 줄).
  3. 그 메모가 에디터에 열려 있으면 에디터를 거쳐 고친다(화면에 바로 보이고 되돌리기 가능, 편집과 충돌하지 않음,
     `replace_range_keeping_selections`). 아니면 파일에 쓴다.
  4. 폴더 감시가 그 파일만 다시 읽어 색인을 갱신한다.
- 순서: 날짜(예정일·마감일)와 메모 안 순서로 정렬한다. 끌어서 정하는 순서가 필요해지면 Obsidian Tasks의 ID
  (`🆔 abc123`)를 붙이고 순서는 따로 저장한다. ID는 위치가 바뀐 할 일을 찾는 데도 쓴다.
- 제외: 할 일이 아닌 체크 목록(준비물 등)을 모은 그룹은 그룹 메타(`.writer.toml`)로 색인에서 뺄 수 있다.
- 전용 그룹: 할 일 화면에서 만든 새 할 일을 적는 기본 메모 그룹이다. 그룹 종류(`GroupKind`)를 하나 더해 할 일
  목록 모양으로 그릴 수 있게 한다. 이 그룹도 다른 메모처럼 스캔되므로 원본은 여전히 원문 하나다.

### 저장 위치 원칙

| 데이터 | 위치 | 동기화 |
| --- | --- | --- |
| 메모 원문(할 일 포함), 사용자가 만든 스키마·설정 | 라이브러리 | 예 |
| 원문에서 언제든 다시 만드는 색인(할 일, 이후 그래프·검색) | OS 캐시 폴더의 redb | 아니오 |
| 다시 만들기 비싼 파생 결과(LLM 등, 이후) | 라이브러리 `.writer/derived/`, 원본 시트마다 파일 하나, 원문 해시·모델·버전과 함께 | 예 |

## 결과 (Consequences)

- (+): 할 일이 원문에 남아 다른 도구(Obsidian 등)와 Git에서 그대로 읽힌다. 따로 저장하는 데이터가 없다.
- (+): 메모 그룹이 곧 할 일의 영역(Things의 영역·프로젝트)이다.
- (+): 회의 메모 중간에 `- [ ]`만 적어도 할 일이 된다. 맥락이 그 자리에 남는다.
- (-): 메모 전체를 훑어야 한다. 처음 한 번만 전체를 읽고 이후에는 바뀐 파일만 읽는다.
- (-): 아무 메모의 아무 줄에 다시 쓰므로, 줄 확인이 실패하면 고치지 못하고 다시 스캔해야 한다.
- (-): ID를 붙이기 전에는 끌어서 정한 순서를 저장할 수 없다.
- (-): 메모를 지우면 그 안의 할 일도 사라진다.
- (-): 이모지 표기는 손으로 치기 번거로워 입력 보조(날짜 고르기, 배지 표시)가 필요하다.

## 정하지 않은 것

- 할 일 전용 그룹의 위치·이름과 전용 화면의 모양.
- 할 일 화면의 보기(오늘·예정·언제든·언젠가·로그북), 상세 패널 편집, 태그 거르기, 반복(`🔁`), 알림의 범위와 순서.
- "언젠가"를 나타내는 방법(예약 태그 등). 표준이 없다.

## 대안 (Alternatives)

| 대안 | 기각 사유 |
| --- | --- |
| 할 일을 앱 데이터베이스(SQLite 등)에 따로 저장 | 원문과 두 벌이 되어 어긋난다. 다른 도구·Git에서 보이지 않는다 |
| 캐시를 JSON 파일 하나로 | 바뀐 메모 하나 때문에 전체를 다시 쓴다 |
| 캐시를 SQLite로 | 이 규모에서는 과하다. 검색·그래프 질의가 필요해지면 다시 본다 |
| 캐시를 라이브러리 안(`.todo.toml` 등)에 | 동기화되며 기기마다 충돌 사본이 생긴다. DB 파일은 동기화 중 깨질 수 있다 |
| ASCII key:value(`due:2026-10-30`) | 치기는 쉽지만 다른 앱에서 일정으로 인식되지 않는다 |
| 프로젝트 원고까지 모으기 | 책 본문의 체크 목록이 할 일로 섞인다 |
| 전용 그룹만 원본으로(할 일 하나 = 시트 하나) | 쓰기·순서·이동은 단순하지만, 메모 속 할 일을 옮겨 적어야 해서 원문 하나를 원본으로 둔다는 원칙과 맞지 않는다 |
