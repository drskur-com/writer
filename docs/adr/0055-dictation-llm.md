# ADR-0055: 받아쓰기는 원문을 바로 기록에 쓰고, 몇 문단씩 모아 LLM이 번역(외국어)하거나 다듬은(사용 언어) 글을 그 묶음 아래 `> …`로 끼워 넣으며, 몇 분마다 요약을 따로 고쳐 쓴다

- 상태: Proposed
- 날짜: 2026-10-25
- 관련: ADR-0054(받아쓰기 모델·기록), ADR-0053(OCR의 LLM 옵션, 같은 원칙), ADR-0048(Token Plan), ADR-0011(줄 하나가 문단) · `src/agent/dictation.rs`(프롬프트·요청·답 읽기), `src/dictation/output.rs`(쓰기 스레드·번역), `src/dictation/recognizer.rs`(인식 작업 스레드), `src/app/dictation.rs`(녹음 막대), `src/app/dictation/ai.rs`(요약), `src/settings.rs`(받아쓰기 페이지), `src/config.rs`(`[dictation]`)

## 배경 (Context)

강의·회의를 받아 적으며 다른 언어로 바로 읽고, 길어지면 지금까지의 요점을 보고 싶다. 받아 적은 글은 군말·잘못 알아들은 단어가 섞인다.

- 받아쓰기(ADR-0054)는 기기 안에서 하고 음성은 밖으로 보내지 않는다. LLM은 설정의 AI 제공자(Bedrock·Token Plan)라 받아 적은 글이 밖으로 나간다.
- 녹음 중인 기록 파일은 인식 작업 스레드만 끝에 덧붙인다. 에디터는 읽기 전용이다(원자적 저장이 파일을 바꿔치우면 덧붙인 문단이 사라진다). 쓰는 쪽이 늘면 같은 문제가 생긴다.
- Nemotron은 언어를 알아서 읽지만 언어 태그를 남기지 않는다. LLM은 글을 보고 언어를 안다.
- 문단은 2초 쉼으로 맺는다. "네." 같은 짧은 문단이 많고, 쉬지 않고 주고받으면 두 사람 말이 한 문단에 섞인다.
- 출력 토큰은 입력보다 비싸고 느리다. 원문은 이미 받아 적어 있다.
- OCR의 "AI로 읽기"(`agent/transcribe.rs`)가 대화 맥락·도구 없이 지시와 입력만 보내는 한 번의 요청이다.

## 결정 (Decision)

**파일 하나에는 쓰는 쪽이 하나다.** 녹음 중 기록에는 쓰기 스레드만, 요약 파일에는 요약 작업만, 녹음 뒤에는 에디터만 쓴다. 인식 작업 스레드는 쓰기 스레드가 남은 문단(번역 포함)을 다 쓸 때까지 기다린 뒤 끝을 알린다.

| 하는 일 | 언제 | 쓰는 곳 | 쓰는 쪽 |
| --- | --- | --- | --- |
| 받아쓰기 원문 | 문단마다 | 기록 끝 | 쓰기 스레드(인식 작업 스레드가 맺은 문단을 채널로 넘긴다) |
| 번역·다듬기 | 몇 문단씩 모아 | 그 묶음의 원문 바로 아래(`> …`) | 쓰기 스레드(번역 스레드의 답을 받아 끼워 넣는다) |
| 요약 | 몇 분마다 | 요약 파일 | 요약 작업 |
| 요약 넣기 | 녹음 뒤 | 기록 | 앱(요약 파일을 읽어 기록에 넣는다) |

**설정 → 받아쓰기에 LLM 옵션을 둔다. 기본은 모두 끔이다.**

- 사용 언어(쓰지 않음 / 16개 언어, 설정의 "녹음 중 번역·다듬기"), 녹음 중 요약(켬·끔, 주기는 `summary_minutes` 기본 5분), 쓸 모델(제공자의 모델 중에서, 제공자별로 저장. 지연이 중요하니 빠른 모델을 권한다. 고르지 않으면 어시스턴트의 모델). AI 제공자를 설정하지 않았으면 설정 → AI를 안내한다.
- 켜면 받아 적은 글이 어느 제공자로 가는지 보인다. 음성은 여전히 보내지 않는다.

**번역·다듬기(near 실시간): 원문은 기다리지 않고 바로 쓰고, 모은 묶음의 답(번역문·다듬은 글)은 그 묶음 아래에 `> …` 줄로 끼워 넣는다.**

- 원문은 문단이 맺히면 바로 기록 끝에 쓴다. 모은 글이 200자를 넘거나 묶음의 첫 문단을 받고 15초가 지나면 그 묶음을 번역 스레드로 넘긴다(1시간에 150–200번쯤). 모델이 느려도 원문은 밀리지 않는다.
- 오디오 언어를 따로 알아내지 않는다. 모델이 문단마다 언어를 보고 고른다: 다른 언어면 군말을 빼고 뜻을 살려 사용 언어로 옮기고(`<tr n="N">`), 사용 언어면 그 언어로 다듬는다(`<fix n="N">`: 군말·되풀이를 빼고 띄어쓰기·문장 부호·맥락으로 보아 잘못 알아들은 말을 고친다. 확실하지 않으면 그대로 두고, 말한 사람의 말씨와 뜻은 바꾸지 않는다). 섞인 문단은 많은 쪽 언어로 본다.
- LLM은 번역문·다듬은 글만 낸다. 원문은 받아쓰기 그대로 남는다(출력 토큰이 절반쯤 준다). 잘못 알아들은 단어는 원문에 남고 `>` 줄에서 바로잡힌다. 고칠 것이 없던 문단은 `>` 줄을 두지 않는다.

  ```
  음 그러니까 오늘 회의는 어 예산 얘기 입니다
  Let's move on to the next topic.
  > 그러니까 오늘 회의는 예산 얘기입니다.
  > 다음 주제로 넘어가겠습니다.
  ```

  (사용 언어가 한국어일 때, 두 문단이 한 묶음. 첫 `>` 줄은 다듬은 글, 둘째는 번역문.)

- 문단마다 번호를 붙여 보내고 같은 번호로 받는다. 개수가 어긋나면 그 묶음을 한 번 다시 보내고, 또 어긋나면 원문만 쓰고 알린다. 형식을 조금 어긴 답(닫는 태그 빠짐, 태그 안의 태그, 예전 꼴 `<p>`·`<same>`)도 읽고, 빈 태그나 태그 조각이 남은 글은 쓰지 않고 원문을 둔다.
- 맥락: 직전 4문단의 원문·기록에 쓴 글과 용어집(최대 60항목)을 "맥락(출력하지 말 것)"으로 함께 보낸다. 묶음마다 새로 나온 고유명사와 그 번역을 `<terms>` 목록으로 함께 받아 용어집에 더한다. 시스템 프롬프트·용어집을 요청 앞에 두어 제공자의 프롬프트 캐시가 들기 쉽게 한다(캐시 지점을 따로 두지는 않았다).
- 번역 스레드는 묶음을 차례로 보낸다(앞 묶음의 답이 다음 묶음의 맥락이다). 쓰기 스레드는 기록 전체(에디터 본문의 줄)를 들고 있다가 답이 오면 그 묶음의 마지막 원문 아래에 끼워 넣고(뒤에서 기다리는 묶음의 자리는 그만큼 민다) 기록을 원자적으로 다시 쓴다. 에디터에는 같은 줄 번호로 끼워 넣는다(녹음 전에 저장했고 녹음 중에는 읽기 전용이라 줄이 같다). 녹음 막대에는 답을 기다리는 묶음 수를 보인다. 답이 실패하거나 30초를 넘기면 그 묶음은 원문만 남는다(네트워크가 끊겨도 받아쓰기는 이어지고, 앱이 죽어도 원문은 이미 기록에 있다). 녹음을 멈추면 남은 묶음의 답까지 받고 끝낸다.

**요약: 몇 분마다 기록과 짝인 요약 파일을 고쳐 쓴다.**

- 요약 파일은 `STT/.summaries/<기록 ULID>.md`다. 점으로 시작하는 폴더라 라이브러리 목록에 시트로 보이지 않는다.
- 기본 5분마다, 직전 요약과 그 뒤로 새로 쌓인 문단만 보내 요약을 고친다. 녹음이 길어도 요청 크기가 일정하고, 1시간에 10–12번쯤이다.
- 요약은 저절로 고쳐지고, 녹음 막대의 "요약 보기"로 막대 위쪽에 따로 된 패널로 펼쳐 본다(앱의 다른 떠 있는 패널과 같은 모양. 머리줄에 요약 주기와 닫기가 있고, 본문은 높이가 정해져 패널 안에서 스크롤한다. 다시 누르면 접는다). 녹음 중에는 요약이 고쳐질 때마다 바로 바뀌고, 녹음이 끝난 뒤에는 고른 기록의 요약 파일을 보인다(요약 넣기 안내에도 "요약 보기"가 있다). 넣거나 버리면 접는다.
- 녹음이 끝나면 남은 원문으로 마지막 요약을 한다. 그 기록을 보고 있으면 녹음 막대에 "이 기록의 요약이 있습니다 · 요약 보기 · 버리기 · 맨 아래에 넣기"를 보인다(넣거나 버릴 때까지 기록을 열 때마다 보인다). 넣으면 기록 맨 끝에 `## 요약`과 글머리표 줄로 넣고 요약 파일을 지운다. 받아 적은 글을 다 읽은 뒤에 보는 정리라 끝에 둔다. 이미 요약 구간이 있으면 지우고 새 끝에 넣는다(이어서 녹음한 뒤에도 요약이 끝에 온다).
- 요약은 글머리표 줄만 쓰게 한다. 이어서 녹음할 때는 요약 파일(없으면 기록의 요약 구간)에서 이어 고친다. 요약 언어는 번역 언어, 없으면 기록의 언어다.

**녹음 뒤 다듬기는 두지 않는다.** 기록은 보통 시트라 오른쪽 AI 어시스턴트에게 다듬기를 맡긴다(전용 버튼은 어시스턴트와 겹친다).

## 결과 (Consequences)

- 좋아지는 점(+): 받아 적으며 다른 언어로 바로 읽고, 긴 녹음의 요점을 녹음 중에도 본다. 쓰는 쪽을 파일마다 하나로 두어 번역·요약을 함께 켜도 기록이 깨지지 않는다. 원문 병기에 출력 토큰을 쓰지 않는다.
- 감수하는 점(-): 켜면 받아 적은 글이 외부 제공자로 나가고, 녹음 시간에 비례해 비용이 든다. 번역은 5–20초 늦다. 원문 병기는 잘못 알아들은 단어를 그대로 둔다. 문단을 쉼으로만 나누므로 여러 사람 말이 한 쌍에 섞일 수 있다. 프롬프트로 막아도 모델이 뜻을 바꿀 가능성은 남는다(원문을 함께 둔다).
- 후속 작업(TODO): 모으는 기준(200자·15초)·시간 제한(30초)·요약 주기를 써 보며 맞추기. Bedrock 캐시 지점 두기. 기록을 지우거나 옮길 때 요약 파일도 함께 옮기기. 기기 안의 작은 모델로 번역하기.

## 대안 (Alternatives)

| 대안 | 기각 사유 |
| --- | --- |
| 문단이 맺힐 때마다 번역 요청 | 짧은 문단마다 요청이 나가 비용·요청 수가 크고, 맥락이 짧아 번역이 어색하다 |
| 녹음 뒤에만 번역 | 받아 적으며 다른 언어로 읽을 수 없다 |
| 답을 기다렸다가 원문과 함께 쓰기 | 모델이 느리면 원문까지 밀려 받아 적은 글이 늦게 보인다 |
| LLM이 원문과 번역문을 함께 내기 | 출력 토큰이 두 배다. 원문은 이미 있다 |
| 번역에 앞 원문만 맥락으로 보내기 | 앞에서 쓴 번역 용어·말투와 어긋난다 |
| 요약을 기록 맨 위에서 고쳐 쓰기 | 작업 스레드가 덧붙이는 파일을 다른 쪽이 고치게 되어 문단을 잃는다 |
| 요약을 기록 끝에 덧붙이기 | 받아 적은 글 사이에 요약이 끼어 읽기 어렵다 |
| 요약할 때마다 기록 전체를 보내기 | 녹음이 길어질수록 요청이 한없이 커진다 |
| 녹음 뒤 "AI로 다듬기" 버튼(묶음으로 나눠 다듬고 diff로 확인) | 만들어 보았으나 AI 어시스턴트로 시트를 다듬는 것과 겹쳐 뺐다 |
| LLM으로 화자 나누기 | 글만으로 짐작해 여러 사람이면 자주 틀리고, 쉼으로 나눈 문단 안의 말 바뀜을 못 맞춘다 |
| 오디오 언어를 따로 알아내기(언어 식별 모델) | 모델이 하나 더 든다. LLM이 글로 안다 |
